# 写拉松插件开发日志 (2026-02-04)

## 1. 用户需求总结
用户今天的主要目标是优化 **Web 剪藏 (Web Clipping)** 的稳定性和内容质量，具体诉求如下：
*   **修复解析失败错误**：解决剪藏时频繁出现的“解析当前页面失败”及“Cannot read properties of null”等崩溃问题。
*   **深度适配微信公众号**：解决微信文章剪藏字数为 0 或排版混乱（文字图片堆叠、无分段）的问题。
*   **支持 AI 对话剪藏**：要求能够识别 **ChatGPT、Gemini、豆包 (Doubao)** 等 AI 平台的对话内容，并自动区分角色（User / AI）。
*   **优化 Markdown 排版**：确保剪藏内容分段清晰，图片与文字之间有合理的空行。

---

## 2. 核心实现过程

### A. 架构重构：模块化解析引擎
*   **建立 `content-parser.ts`**：将解析逻辑从 `Clipper.tsx` 视图组件中剥离，建立独立的解析策略层。
*   **静态导入优化**：放弃了会导致插件环境运行不稳定的动态 `import()`，改为静态 `import` `ReadabilityLite` 和 `TurndownService`，确保打包后的 JS 执行路径万无一失。

### B. 微信公众号专项适配
*   **靶向定位**：锁定微信正文唯一标识 `#js_content`。
*   **标签强制转换**：针对微信大量使用 `div/section` 导致排版堆叠的问题，实现了一套递归算法，在解析前将所有块状容器强制转换为标准 `<p>` 标签。
*   **延迟加载支持**：适配微信特有的 `data-src` 和 `data-original` 图片属性。

### C. AI 对话区分识别
*   **ChatGPT/OpenAI**：通过 `[data-message-author-role]` 属性精准提取对话角色。
*   **Gemini/Bard**：
    *   **广谱适配**：覆盖标准版及自定义 Gems，支持 `<message-content>`, `[data-test-id]`, `.model-response-container` 等多种容器。
    *   **用户提问捕获**：增加对 `.user-query` 和 `.query-text` 的显式支持，防止被过滤器误删。
    *   **时序校准**：引入 DOM 物理位置排序 (`compareDocumentPosition`)，确保用户提问和 AI 回答严格按页面显示顺序排列。
*   **豆包 (Doubao)**：
    *   **减法策略**：克隆消息节点，剔除思考过程块，提取剩余内容作为正式回答。
    *   **思考过程引用化**：识别并提取思考过程，自动添加 `> [思考过程]` 引用前缀。
*   **对话分层**：在不同角色的对话间自动注入 `---` 分割线，增强可读性。

---

## 3. 重要错误记录与解决

| 错误现象 | 根本原因 | 解决方法 |
| :--- | :--- | :--- |
| **解析当前页面失败** | 异步加载 `turndown` 模块在插件环境下失效 | 改为**静态导入**，合包编译 |
| **Cannot read properties of null** | `DOMParser` 解析失败或 `Readability` 找不到 body | 增加了严格的**空值校验 (Null Check)** 和解析回退机制 |
| **剪藏字数为 0** | 微信公众号排版不使用标准 `p` 标签，导致算法漏检 | 引入**高置信度选择器清单**，优先匹配已知平台容器 |
| **排版粘连/无分段** | `Turndown` 将微信嵌套的 `section` 识别为行内元素 | **递归标签转换**：解析前暴力将 `section/div` 转为 `p` 标签 |

---

## 4. 目前成果
1.  **稳定性**：解决了所有已知的运行时崩溃和模块加载错误。
2.  **内容质量**：
    *   微信公众号文章现在能够完整提取，包含图片，且分段自然。
    *   主流 AI 对话界面支持一键剪藏，且自带 Markdown 角色标注。
3.  **统一入口**：不论是当前页直接剪藏还是手动输入 URL 解析，均使用同一套高性能解析引擎。
